## ParamElemExternal probe result (pee/pee2, 2024 Structural, Rebar Shape family "00")

All 12 ids Revit adds to the lifted family (187616..187627) EXIST in the project with captions A,B,C,D,E,F,G,H,J,K,O,R-style (Rebar Shape dimension parameters) and each carries m_externalParamKey.m_guidValue. So the fix is a pure closure rule, no new data needed: add the project ParamElemExternal elements that the family's shared parameters refer to (same shared GUID as the family's parameter, or the ids listed in the family's Global/ContentDocuments/ParamElemFamily records), copy them into the rfa partition (m_famId := family id like the other shared elements), append them to Family.m_familyIds with consecutive m_index and bump m_nextAbsorbedIndex by the count, and insert their ids into the m_deletion list in sorted position (diff in lift_cmp output). Same rule should cover the 3 Generic Models/Structural Columns families that are 2 parameters short.

## 2026-specific H-record difference (from lcall26 vs lcall, 2024): the extra ~3,200 differing H records in 2026 are almost all GStyleElem `m_parents.m_deletion`: our list is [own id, family id], Revit's 2026 is [family id, own id] (e.g. own 1032722, family 951192: Revit writes 951192 first). 2024 does not show this diff (append matches). So for format 2026 insert the family id at the FRONT of m_deletion of the shared standard elements (rvtx/rfa.py, the "m_deletion += family id" step; keyed by year). Expected effect: 2026 H identity from 98.29% to about 99.3% (the 2024 level). Other H diffs are common to both years: Family record deletion shift (the shared-parameter closure), SunAndShadowSettings/DBView* m_abFlags4Bytes, LinearDimString/Alignment appearanceParents/regenOnly lists.

Update on the 2026 m_deletion order: three attempted rules were measured with tools/lift_cmp.py over all 177 families and REJECTED (H identity 2026: baseline 98.29%): "family id first for every shared element" 17.4%; "... only for shared GStyleElem" 22.9% (note: the H body tag is a generic header tag, the class must be taken from the R body); "swap for the family's own GStyleElem" no change (those are not the differing ones). So only SOME shared GStyleElem need the family id first; the discriminator is not the class alone (ids around 1032722 differ; other GStyleElem append fine). Needs a per-record look: compare the project's original m_deletion for a differing GStyleElem and a matching one in one 2026 family (lift_cmp prints both) to find the rule. Not merged; rvtx/rfa.py on branch test is unchanged by this.

Measured and rejected (lift_cmp, 177 families, 2024 and 2026): setting m_abFlags4Bytes |= 0x10000 on every DBView* and |= 0x4 on every SunAndShadowSettings of the family's own records: H differing records 2024 2,323 -> 4,538 and 2026 2,646 -> 4,861 (about +2,200 each).
